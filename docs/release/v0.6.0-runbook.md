# v0.6.0 Release & Rollback Runbook — Direct Push Guard

> This document **only describes** the process. It does **not** authorize any
> merge, tag, or publication. Each step marked **[AUTH]** needs explicit,
> separate authorization before execution.

## SHA relationships (coherence model)
| Reference | What it points to | Mutable? |
| --- | --- | --- |
| **Composite action SHA** | commit that contains `actions/direct-push-guard/action.yml` + `scripts/governance/*.mjs` | immutable (full 40-hex) |
| **Reusable workflow SHA** | the commit a consumer pins `reusable-direct-push-guard.yml@<sha>` to | immutable |
| **Release commit SHA** | the `main` commit after PR #5 is merged | immutable |
| **`v0.6.0` tag** | annotated tag → the release commit | should be immutable by policy |

Key rule: the reusable workflow and the composite **need not share a SHA**. The
composite is currently pinned to `@fffd1a1` (immutable, contains the tested
implementation). That pin **may remain** as long as `fffd1a1` stays reachable in
`main` history.

### Merge-strategy requirement (avoids a broken pin)
`fffd1a1` is a feature-branch commit. To keep the composite pin resolvable after
release:
- **Merge PR #5 with a merge commit** (not squash/rebase) so `fffd1a1` becomes an
  ancestor of `main` and stays reachable; **or**
- after merge, **re-pin** the composite to the release commit with
  `scripts/release/pin-composites.sh --apply --only direct-push-guard <release-sha>`
  (its coherence guard verifies the SHA contains the action + scripts), then
  commit that change before tagging.

Do **not** squash/rebase-merge and then delete the feature branch without
re-pinning — that can orphan `fffd1a1` and break consumers.

## Release sequence
1. **[AUTH] Review & approve PR #5** (`feature/reusable-direct-push-guard` → `main`). Verify central CI is green.
2. **[AUTH] Merge PR #5 into `main`** using a **merge commit**. Do not merge any other way without re-pinning (see above).
3. **Verify the resulting `main` commit**: `git fetch && git log --oneline -3 origin/main`; confirm it contains `actions/direct-push-guard/action.yml`, `scripts/governance/*.mjs`, and the reusable workflow.
4. **Validate composite references & CI on `main`**:
   - `scripts/release/pin-composites.sh --only direct-push-guard <composite-sha>` (dry-run) → confirms the pin is coherent.
   - Confirm the `CI - Direct Push Guard` workflow is green on `main`.
   - `grep -n "actions/direct-push-guard@" .github/workflows/reusable-direct-push-guard.yml` → a 40-hex SHA, reachable from `main`.
5. **[AUTH] Create the annotated tag** (separate authorization, after step 4):
   `git tag -a v0.6.0 <release-sha> -m "Direct Push Guard (detective audit)"` then `git push origin v0.6.0`.
6. **Verify the tag** points to the intended commit: `git rev-list -n1 v0.6.0` equals `<release-sha>`.
7. **Test invocation using the published release** from the disposable repo
   (`security-ci-test`): a caller pinned `reusable-direct-push-guard.yml@v0.6.0`
   (or the release SHA) runs scenarios A/B in **audit** mode and classifies
   `DIRECT_PUSH` / `AUTHORIZED_PR_MERGE` as validated.
8. **Prepare consumer migration** (see the caller example and the permissions
   requirement). Consumers start in `audit` mode, grant `contents: read` +
   `pull-requests: read`, and pin by immutable SHA (comment the tag).

## Rollback runbook
No tag deletion or history rewrite is ever required for rollback.
1. **Consumer revert**: change the caller's `uses:` back to the previously
   validated reference (e.g. the prior release SHA/tag), commit, open a PR, merge
   via the consumer's normal process. The guard is detective, so reverting it has
   no deployment impact.
2. **Restore a previous caller configuration**: keep the prior caller file in
   version control; `git revert` the commit that changed it, or re-apply the
   known-good file. Re-grant the required permissions.
3. **Verify the rollback via GitHub Actions**: on the next push, confirm the
   `Direct Push Guard` job runs the expected (reverted) reference and reports the
   expected classification; check the run URL + job summary.
4. **Preserve audit evidence**: do **not** delete prior runs, branches, PRs, or
   job summaries. They are the audit trail. Archive run URLs in the incident notes.
5. **Never rewrite or delete a published tag.** To supersede `v0.6.0`, publish a
   new patch (e.g. `v0.6.1`); leave `v0.6.0` in place.
6. **Do not touch `v0.5.0`** or any production repository during rollback.
